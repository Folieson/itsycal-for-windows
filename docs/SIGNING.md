# Signing and distribution

Itsycal for Windows ships as a **signed MSIX package**. This document covers why the
signature is mandatory, which certificate options exist for an open-source project, the
GitHub secrets and commands involved, and how to rotate certificates.

## Why the MSIX signature is not optional

PowerToys Command Palette finds extensions only through the MSIX app-extension catalog
(`AppExtensionCatalog.Open("com.microsoft.commandpalette")`). An unpackaged install that
registers a COM server under `HKCU` is not discovered by Command Palette, so the earlier
Inno Setup / unpackaged distribution idea was dropped (see
[PowerToys issue #44442](https://github.com/microsoft/PowerToys/issues/44442) and
[ADR 0001](adr/0001-windows-command-palette-extension.md)).

Windows also enforces the identity at install time:

- the package `Publisher` in `Package.appxmanifest` must match the signing certificate, and
- the certificate must chain to a root the machine trusts.

WinGet's `InstallerType: msix` support relies on that: the manifest's `SignatureSha256`
is the SHA256 of the `AppxSignature.p7x` entry inside the package, and `winget install`
refuses a package whose signature is not trusted. A self-signed package works only after
the user imports its `.cer` into `LocalMachine\TrustedPeople`, which is acceptable for
development and **not acceptable for WinGet**.

## Options for an open-source project

| Option | Cost | Certificate trust | How it fits this repository |
|---|---|---|---|
| [SignPath Foundation](https://signpath.org/) | Free for eligible OSS projects | Trusted root, signing happens in SignPath's service | Apply with the project; SignPath signs the built package. The PFX secrets below are then unnecessary, but the release workflow must call the SignPath service instead of `Build-Release.ps1 -CertificatePath`. |
| [Certum Open Source Code Signing](https://certum.eu/) | Free or discounted certificate for OSS maintainers; verify current terms | Trusted root | Issued to the maintainer/project after identity verification. Export it as a PFX and use the `SIGNING_PFX_*` secrets; no workflow change needed. |
| Microsoft Store | Partner Center registration may be free for individual accounts; company accounts cost money | Store-signed, trusted | Alternative distribution channel. The Store identity and signing are managed by Microsoft; for WinGet use an `msstore` installer manifest (Store product ID) instead of a raw MSIX URL. Do not submit a Store-signed package as a sideloading `msix` manifest. |
| Self-signed development certificate | Free | Not trusted | Generated by `Build-Release.ps1 -SelfSigned` and by `windows-build.yml`. Users must trust the `.cer`; never submit such a build to WinGet. |

Whichever trusted option you pick, the certificate subject (the `CN=...` part) must equal
the `Publisher` in `windows/src/ItsycalForWindows/Package.appxmanifest`. Changing the
Publisher is a release-sensitive identity change (it also changes the package family
name) вЂ” do it deliberately in its own PR, together with the WinGet manifest update.

## GitHub secrets

| Secret | Required | Purpose |
|---|---|---|
| `TRUSTED_SIGNING_PFX_BASE64` | for a trusted release | Base64 of the code-signing `.pfx`. Its presence switches `.github/workflows/release.yml` from a self-signed development build to a signed release. |
| `TRUSTED_SIGNING_PFX_PASSWORD` | with `TRUSTED_SIGNING_PFX_BASE64` | Password of that `.pfx`. |
| `WINGET_PAT` | optional | GitHub token allowed to fork `microsoft/winget-pkgs` and open the WingetCreate pull request. Without it the workflow still attaches the prepared manifests to the release. |

Set them with the GitHub CLI (never commit the files):

```powershell
# Export the certificate to a PFX from the Windows certificate store
$cert = Get-ChildItem Cert:\CurrentUser\My | Where-Object Thumbprint -eq '<thumbprint>'
Export-PfxCertificate -Cert $cert -FilePath itsycal-signing.pfx `
  -Password (Read-Host -AsSecureString 'PFX password')

# Base64-encode the PFX and store both values as repository secrets
[Convert]::ToBase64String([IO.File]::ReadAllBytes('itsycal-signing.pfx')) |
  Set-Content -NoNewline signing-pfx.b64

gh secret set TRUSTED_SIGNING_PFX_BASE64   --repo Folieson/itsycal-for-windows < signing-pfx.b64
gh secret set TRUSTED_SIGNING_PFX_PASSWORD --repo Folieson/itsycal-for-windows
gh secret set WINGET_PAT           --repo Folieson/itsycal-for-windows
```

If the CA delivers a PEM key and certificate instead of a PFX, either import them into
`Cert:\CurrentUser\My` and export the PFX as above, or convert them:

```sh
openssl pkcs12 -export -out itsycal-signing.pfx \
  -inkey signing-key.pem -in signing-cert.pem -certfile chain.pem
```

The release workflow writes the decoded PFX to `$RUNNER_TEMP` (outside the checkout) and
deletes it in a `finally` block; `windows/.gitignore` also excludes `*.pfx` and `*.cer`.

## Verify a signed package

```powershell
# Trust and publisher check against the package identity
Get-PfxCertificate -FilePath itsycal-signing.pfx -Password (Read-Host -AsSecureString) |
  Select-Object Subject, NotAfter
Get-Content windows/src/ItsycalForWindows/Package.appxmanifest |
  Select-String 'Publisher='

# Signature and (for trustable certificates) Authenticode verification
signtool verify /pa /fd SHA256 .\ItsycalForWindows_1.0.0.0_x64.msix
```

`Build-Release.ps1` runs `signtool verify /pa` for trusted certificates and, for
self-signed builds, only checks that the package contains the `AppxSignature.p7x`
signature block. It writes hashes used by WinGet to `build-info.json`:

```powershell
# The WinGet SignatureSha256: SHA256 of the signature block inside the MSIX
$zip = [IO.Compression.ZipFile]::OpenRead('.\ItsycalForWindows_1.0.0.0_x64.msix')
$entry = $zip.Entries | Where-Object FullName -eq 'AppxSignature.p7x'
$hash = [Security.Cryptography.SHA256]::Create().ComputeHash($entry.Open())
([BitConverter]::ToString($hash) -replace '-', '')
```

## Rotation and expiry

1. **Track the expiry date.** Code-signing certificates for OSS are usually valid for one
   year. `Get-PfxCertificate` (above) shows `NotAfter`; check it at every release and add a
   calendar reminder.
2. **Renew before expiry.** Request the renewal early; the new certificate can be issued
   while the old one is still valid.
3. **Rotate the secrets.** Upload the new PFX with the procedure above, then delete the
   old secret values (GitHub keeps secret history out of the repository, but the values
   themselves are replaced).
4. **Publish a maintenance release.** The new certificate changes `SignatureSha256`, so
   the WinGet manifest must be updated with a fresh build; never re-sign or replace assets
   of an already published release.
5. **Update WinGet.** After the first package is accepted in `microsoft/winget-pkgs`, the
   `WINGET_PAT`-gated workflow step runs `wingetcreate update` and opens the submission
   PR. Without the secret, run `wingetcreate update Folieson.ItsycalForWindows --version
   <version> --urls <x64-url> <arm64-url> --submit` manually.
6. **If the PFX or secrets leak:** revoke the certificate with the CA, rotate both
   secrets, publish the next release with the replacement certificate, and report the
   incident. Do not rewrite already published tags or assets.

## WinGet submission checklist

- [ ] The release was built with a **trusted** certificate (`BUILD_KIND=trusted` in the
      workflow log), not the self-signed development certificate.
- [ ] `PackageFamilyName` in
      `winget/Folieson.ItsycalForWindows/<version>/Folieson.ItsycalForWindows.installer.yaml`
      matches the signed package:
      `Get-AppxPackage ItsycalForWindows | Select-Object PackageFamilyName`.
- [ ] `InstallerSha256` and `SignatureSha256` are real values, not placeholders. The
      release workflow attaches `ItsycalForWindows_<package-version>_winget-manifests.zip`
      with both filled in from `build-info.json`.
- [ ] The locale manifest still contains the `windows-commandpalette-extension` tag.
- [ ] Release asset URLs are publicly downloadable: WinGet clients do not authenticate, so
      the repository/releases must be public (or the assets must be served from a public
      location).
- [ ] The **first** submission is manual (`wingetcreate new <x64-msix-url>
      <arm64-msix-url>`); `wingetcreate update --submit` only works once the package
      exists in `microsoft/winget-pkgs`.
- [ ] After acceptance, users can install with `winget install
      Folieson.ItsycalForWindows`; Command Palette then lists the extension through the
      WinGet source.
